# Харчоблок — система обліку лікувального харчування

Многопользовательская веб-система для пищеблока одной больницы (пилот). Заменяет бумажный
документооборот: замовлення відділень → план меню → розхід продуктів → списання в бухгалтерії.
Нормативная база — Наказ МОЗ України №931 від 29.10.2013.

Перед любой работой прочитай `docs/` — там доменная модель, схема данных, workflow-движок,
UI и план спринтов. Этот файл — сжатые правила; подробности в docs.

## Стек (не менять без обсуждения)

- Python 3.12, Django 5.x, PostgreSQL 16
- HTMX + Bootstrap 5 (без SPA, без Node-сборки; статика через WhiteNoise)
- django-simple-history (аудит справочников), django-environ (конфиг)
- pytest + pytest-django, factory_boy
- Docker Compose: `web` (gunicorn), `db` (postgres), `caddy` (HTTPS), `backup` (pg_dump по крону)
- Хостинг: Hetzner Cloud (CX22), домен с автоматическим TLS через Caddy

## Язык

- Интерфейс, сообщения, названия в админке — **українською**. Всё через `gettext`, `LANGUAGE_CODE = "uk"`.
- Код, имена моделей/полей, комментарии, коммиты — английский.
- `TIME_ZONE = "Europe/Kyiv"`, `USE_TZ = True`.

## Структура проекта

```
harch/
  config/            # settings (base/dev/prod), urls, wsgi
  apps/
    accounts/        # User, роли, привязка к відділенню
    catalog/         # Product, Diet, Dish (картка-розкладка), DishIngredient
    menus/           # Menu (№, дієта), MenuItem (прийом їжі → страва)
    orgstructure/    # Department (відділення)
    orders/          # DailyOrder, DailyOrderLine (відділення × дієта × порції)
    planning/        # DailyPlan, DailyPlanEntry (дата × дієта → меню)
    consumption/     # расчёт розходу, снапшоты, фактичний розхід
    workflow/        # Task, TaskEvent, Notification, реестр типов задач
    reports/         # экспорт PDF/XLSX, накопичувальна відомість
    assist/          # ИИ: клиент Anthropic, журнал вызовов, импорт карток по фото
  templates/         # base.html с левым сайдбаром, partials для HTMX
  seed/              # JSON из Excel-прототипа + management command load_seed
  docs/
```

## Инварианты домена — НЕ НАРУШАТЬ

1. **Меню принадлежит ровно одной дієті.** `Menu.diet` обязателен. В плане дня для дієти D можно выбрать только меню с `diet == D`.
2. **План дня = одно меню на каждую дієту, у которой есть порции.** Уникальность `(date, diet)` в `DailyPlanEntry`.
3. **Замовлення відділення — разбивка по дієтам.** Строка = `(order, diet, portions)`. Відділення имеет `default_diet`, но медсестра может указать порции по нескольким дієтам.
4. **Расчёт розходу:** `розхід(продукт) = Σ_дієта порції(дієта) × Σ_страва_в_меню брутто(продукт в страві)`. Брутто — для закупівлі/списання, нетто — для БЖУ/ккал.
5. **Снапшот при утверждении.** Когда план дня утверждён, расчёт фиксируется в `ConsumptionSnapshotLine` (копии норм на момент утверждения). Последующие правки карток **не меняют** историю. Бухгалтерия работает только со снапшотами.
6. **Картки-розкладки версионируются** (simple-history). Изменение картки влияет только на будущие планы.
7. **Maker ≠ checker.** Пользователь не может утвердить задачу, которую сам сдал. Отклонение требует комментария. Админ не утверждает вовсе. Исключение — замещение (S7-06): второй вход той же человека (`User.main_login`) может утвердить поданное первым, но это помечается в истории и сообщается админам.
8. **Объект редактируем только пока его задача у maker'а** (`pending`/`in_progress`/`rejected`). После `submitted` — read-only, после `approved` — заблокирован навсегда (правка = новая корректирующая задача).
9. **Никаких персональных данных пациентов.** Только количества порций по відділенню и дієті. Не добавлять ФИО, диагнозы, номера історій хвороби.

## Роли

`admin`, `dietician` (дієтсестра / лікар-дієтолог), `chef` (завідувач виробництва), `dept_nurse`
(старша медсестра відділення, FK на Department), `accountant` (бухгалтер). Роль — поле `User.role`
(choices), не Django Groups. Доступ через миксины `RoleRequiredMixin(roles=[...])` и фильтрацию
querysets по відділенню для `dept_nurse`. Подробно — `docs/04_ui.md`.

## Workflow (maker/checker)

Каждый handoff между ролями — `Task` со статусами
`pending → in_progress → submitted → approved | rejected → (resubmitted) submitted …`.
Типы задач и их цепочки — в реестре `apps/workflow/registry.py`, не хардкодить в views.
Переходы только через сервис `apps/workflow/services.py` (`start`, `submit`, `approve`, `reject`),
каждый переход пишет `TaskEvent` и создаёт `Notification`. Подробно — `docs/03_task_engine.md`.

## ИИ (Anthropic API)

ИИ готовит черновики, человек решает. Результат модели — только черновик у maker'а с пометкой
«Запропоновано ШІ»; никаких автоматических сохранений, submit или approve. Расчёты розходу/БЖУ
и переходы workflow — никогда не через модель. Система полностью работает без ИИ.
Вызовы модели — только через `apps/assist/client.py`, каждый пишется в `AIRequestLog`.
`ANTHROPIC_API_KEY` — только в `.env`; не коммитить, не логировать, не выводить в UI.
В тестах реальный API не вызывается. Подробно — `docs/07_ai.md`.

```bash

```

## Правила разработки

- Бизнес-логика — в `services.py` каждого app, не во views и не в `save()`. Views тонкие.
- Расчёт розходу — чистая функция `apps/consumption/calc.py`, покрыта unit-тестами с ручными примерами (см. `docs/02_data_model.md`, раздел «Контрольный пример»).
- Все количества хранить в граммах как `DecimalField(max_digits=12, decimal_places=2)`; килограммы — только при отображении.
- Каждая модель с датой обслуживания использует поле `service_date` (дата, на которую готовится еда), не `created_at`.
- Любая новая фича — тест на happy path + тест на права доступа (чужое відділення, чужая роль).
- Миграции не редактировать задним числом после деплоя.
- Коммиты маленькие, по одному тикету из `docs/05_sprints.md`; в сообщении — ID тикета (`S2-03: ...`).

## Что НЕ делать в v0.1

Telegram-бот, КЕП/электронная подпись, интеграция с МІС/ЕСОЗ, индивидуальные назначения пациентам,
аллергии, мобильное приложение, multi-tenancy. Всё это в `docs/05_sprints.md` → «Бэклог v0.2+».

## Важно про seed-данные

`seed/*.json` извлечены из Excel-прототипа. Нормы БЖУ — справочные средние значения, картки и
250 меню сгенерированы как стартовый набор. **Перед боевым использованием дієтсестра должна
проверить и утвердить картки.** В UI справочника показывать бейдж «Не перевірено» у записей с
`verified=False` (все seed-записи грузятся с `verified=False`).
