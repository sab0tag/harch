# 07. ИИ в системе

## Принцип

**ИИ готовит черновик, человек решает.** Любой результат модели попадает в систему только как
черновик у maker'а с пометкой «Запропоновано ШІ». Сохранить, подать или утвердить может только
человек. Автоматических approve нет и не будет.

## Где ИИ нельзя использовать

- Расчёт розходу, БЖУ, ккал, списання — только детерминированный код (`consumption/calc.py`).
- Любые переходы задач в workflow.
- Данные пациентов (их в системе нет и не будет).
- Система обязана полностью работать без ИИ: нет ключа, API недоступен, фича выключена → все
  экраны работают, просто не показываются кнопки ИИ.

## Ключ и настройки

```
AI_ENABLED=false                  # глобальный выключатель
ANTHROPIC_API_KEY=                # только в .env на сервере; никогда в git, в чатах, в логах
ANTHROPIC_MODEL=claude-sonnet-5   # модель задаётся конфигом, не хардкодом
ANTHROPIC_MODEL_LIGHT=claude-haiku-4-5   # дешёвая модель для текстовых задач (AI-10); пусто = всё на основной
AI_DAILY_REQUEST_LIMIT=200        # защита от случайного перерасхода
```

**AI-10 Модель по функции.** `client.model_for(feature)`: на лёгкую модель (`LIGHT_FEATURES` в
`apps/assist/client.py`) идут `reference_duplicates`, `menu_review`, `dish_draft` — только текст, результат
всегда смотрит человек, числа пересчитывает система. На основной остаются фото карток (AI-02, нужна
точность) и оценка БЖУ продуктов (AI-06). Перевод фото на лёгкую модель — только если она проходит порог
AI-04 на эталонных фото. Модель каждого вызова пишется в `AIRequestLog.model`; «Перевірити з'єднання»
пингует обе модели. Haiku 4.5 примерно в 2 раза дешевле Sonnet 5, контекст 200K (нам хватает).

- Отдельный ключ под этот проект; в консоли Anthropic выставить месячный лимит расходов.
- Ключ читается один раз в `apps/assist/client.py`; нигде больше не упоминается.
- В тестах реальный API не вызывается никогда — клиент подменяется фейком.

## Модуль `apps/assist`

```python
class AIRequestLog(Model):            # журнал каждого вызова
    user = ForeignKey(User)
    feature = CharField()             # "card_import", ...
    model = CharField()
    status = CharField(choices=[ok, error, rejected_by_limit])
    input_tokens, output_tokens = PositiveIntegerField(null=True)
    duration_ms = PositiveIntegerField(null=True)
    request_meta = JSONField()        # размер файла, число страниц — НЕ содержимое
    response_json = JSONField(null=True)
    error = TextField(blank=True)
    created_at = DateTimeField(auto_now_add=True)
```

`client.py` — единственная точка вызова модели:
`extract(feature, system_prompt, content_blocks, tool_schema) -> dict`. Структурированный ответ
получаем через принудительный вызов инструмента (tool use) с JSON-схемой, а не парсингом текста.
Проверка лимита, запись в журнал, таймаут и один ретрай — внутри клиента.

## Фича 1 (Sprint 1A): оцифровка карток-розкладок

**Сценарий.** Дієтсестра фотографирует бумажную картку-розкладку или страницу сборника →
загружает на экран «Імпорт картки» → через 10–20 секунд видит слева фото, справа
заполненную форму картки → правит → «Створити картку». Картка создаётся с `verified=False`,
`origin="ai_import"` и ссылкой на черновик.

**Что извлекает модель (схема инструмента):**
```json
{
  "dish_name": "string",
  "card_no_on_paper": "string|null",
  "output_g": "number|null",
  "category_guess": "string|null",
  "ingredients": [
    {"product_raw": "string", "brutto_g": "number|null", "netto_g": "number|null",
     "confidence": "high|medium|low"}
  ],
  "technology": "string|null",
  "source": "string|null",
  "warnings": ["string"]
}
```
Правило в промпте: если число не читается — `null` и предупреждение, **никогда не угадывать**.

**После модели — детерминированная обработка:**
1. Сопоставление `product_raw` со справочником продуктов: точное совпадение → нечёткое
   (нормализация регистра/пробелов/«ё-е», difflib ≥ 0.85) → иначе «Новий продукт?» (создаёт
   только человек, с вводом БЖУ).
2. Проверки: нетто ≤ брутто; нет пустых чисел; сумма нетто правдоподобна относительно выхода;
   дубль названия с существующей карткой.
3. Всё проблемное подсвечивается на форме жёлтым/красным; кнопка «Створити» активна только
   когда нет красных ошибок.

**Модели:**
```python
class DishImportDraft(Model):
    uploaded_by = ForeignKey(User)
    image = ImageField()              # хранится в media/, ужимается до 2000px по длинной стороне
    status = CharField(choices=[processing, ready, failed, accepted, discarded])
    extracted = JSONField(null=True)  # сырой ответ модели
    ai_log = ForeignKey(AIRequestLog, null=True)
    dish = ForeignKey(Dish, null=True)  # созданная картка после accept
```

**Доступ:** admin, dietician.

## Оценка качества до включения пользователям (AI-04)

Это обязательный шаг, а не «потом».
- Набор 15–20 реальных фото карток из больницы + вручную набранный эталон (`evals/cards/*.json`).
- `python manage.py eval_card_import evals/cards/` → отчёт: доля верно извлечённых названий
  продуктов, точность чисел брутто/нетто (точное совпадение), доля полей, где модель честно
  вернула `null` вместо ошибки.
- Порог включения: ≥ 95% чисел точно, 0 «уверенных» ошибок (confidence=high, но число неверно).
- Прогонять при смене модели или промпта. Результаты хранить в `evals/reports/`.

## Где вставить ключ (сделано в AI-01)

- Файл `.env` на сервере (рядом с `compose.yml`): `AI_ENABLED=true`, `ANTHROPIC_API_KEY=sk-ant-...`,
  затем `docker compose up -d`.
- Экран «ШІ-помічник» (`/ai/`, только admin): включено ли, есть ли ключ (сам ключ не показывается),
  расход за день/месяц, журнал вызовов, кнопка «Перевірити з'єднання».
- С сервера: `python manage.py ai_check --ping`.

## Sprint 1B — ИИ-наполнение справочников

Статус: AI-09, AI-08, AI-07 сделаны; AI-06 сделан в варианте «оценка модели» (значения помечены
`origin=ai_estimate`, «Не перевірено», висят в ночной проверке до подтверждения дієтсестрой).
Импорт из фото/PDF таблиц хімічного складу — когда будут реальные страницы справочника.

Общее правило то же: модель предлагает, человек утверждает, всё создаётся с `verified=False`,
`origin="ai_*"`. **Числа модель не выдумывает** — БЖУ, брутто/нетто и ккал берутся из источника
или считаются кодом; ИИ отвечает за разбор, сопоставление и тексты.

**AI-06 Продукты: импорт хімічного складу из справочника.** Дієтсестра загружает фото/PDF страницы
таблиц хімічного складу (довідник, ДСТУ, ТУ постачальника) → модель извлекает строки
«продукт — білки/жири/вуглеводи/ккал на 100 г» → сопоставление со справочником (как в AI-03) →
экран сравнения «зараз / пропозиція / джерело (сторінка)» → человек принимает построчно.
Поле `source` обязательно. Без источника цифры не принимаются.
Попутно: нормализация названий, одиниці, категорія, пропозиція відходів для сезонних норм.

**AI-07 Картки: чернетка новой картки по назві страви.** «Сирники зі сметаною, вихід 150 г» →
модель предлагает состав из **существующих** продуктов и технологию; брутто/нетто рассчитывает
код по `SeasonalWasteNorm`, БЖУ — по справочнику продуктов. Показывается, в какие дієти картка
проходит по нормам. Картка — черновик до проверки дієтсестрой.

**AI-08 Меню: новые варианты под норму дієти.** Подбор блюд — детерминированный алгоритм
(перебор/ЛП): цель — ккал и БЖУ дієти, ограничения — теги дієти (№1а/№4/№9), без повторов блюд
за день и за N дней ротации, сезонность. ИИ — только совместимость/разнообразие («дві каші
поспіль») и короткое пояснение выбора. Первое применение: 234 из 250 стартовых меню ниже нормы
ккал — «Підігнати під норму» предлагает замены/порции для существующих меню.

**AI-09 Проверка справочника.** Отчёт «підозрілі записи»: нетто > брутто, ккал ≠ 4·Б+9·Ж+4·В
больше чем на 10%, дубли продуктов с разными названиями, картки без технології. Проверки — код;
ИИ — только группировка дублей по смыслу («Олія соняшникова» / «Олія рафінована»).

*Сделано (`apps/catalog/audit.py`).* Каждую ночь в 02:40 (`deploy/crontab`) — `audit_reference --ai`.
Правила кодом: ккал ≠ 4·Б+9·Ж+4·В > 10%, похожие названия (цифры должны совпадать: 2,5% ≠ 3,2%),
продукты без цены (списання не подать), оценки ШІ без подтверждения, картки без состава / технології,
выход против суммы нетто, меню вне норм дієти (ккал и БЖУ), блюда, не разрешённые для дієти.
Зауваження привязано к объекту и живёт между прогонами: исправили → «Виправлено» само, вернулось →
снова открыто, «Не проблема» — только с комментарием и остаётся закрытым. Появилось новое →
уведомление дієтсестрі и admin со ссылкой на «Перевірку довідника». ИИ (если включён) только
группирует названия, которые могут означать один продукт; неизвестные id и низкая уверенность
отбрасываются кодом. Недельная `run_checks` (PR #9) влита сюда и удалена — одна проверка, один экран.

**AI-10 Технології з ШІ для існуючих карток.** Для карток без «Технології приготування»
(130 seed-карток) модель пишет 3–6 предложений только по составу картки и дієтам (ЩД/№1а — без
смаження, №9 — без цукру), граммы не повторяет и продуктов не добавляет. 10 карток на вызов
(`feature="dish_technology"`). Предложения — `AIDraft(kind=technology)`, в картку ничего не пишется,
пока дієтсестра не примет (можно поправить текст); принятая картка → «Не перевірено», история с
причиной. Если технологию уже кто-то заполнил — не перезаписывается. Экран «Картки-розкладки →
Технології з ШІ» (по кнопке — одна пачка), для всех разом — `python manage.py draft_technology --limit 130`.
Это заготовка: технология из реальных карточек больницы (перенос — позже) авторитетнее.

**Токени (AI-11).** Все вызовы — через `client.extract` → структурированный вывод
(`output_config.format`, JSON-схема): описание инструмента в запрос не идёт, и это единственная форма,
которую принимает Claude Opus 5.5 (принудительный `tool_choice` у него — 400). Схемы приводятся к
строгому виду в коде (`additionalProperties: false`, без `minItems`/min/max — это проверяет код).
Модели: основная `claude-opus-5-5`, лёгкая `claude-haiku-4-5` — на неё идут дубли, оценка меню,
чернетка картки и технології (текст, который человек всё равно проверяет). Размышления у Opus 5.5
выключить нельзя — рычаг `effort`: по умолчанию `low` (`AI_EFFORT`), `medium` только там, где
модель читает цифры (оценка продуктов, фото карток). Haiku без размышлений. Кэш промптов не
используем: префиксы короткие, вызовы разовые — запись в кэш стоила бы дороже. Batch API (−50%)
для `draft_technology` не делали: 130 карток на Haiku — копейки, асинхронность дороже в поддержке.

Порядок: AI-09 (дёшево, сразу польза) → AI-06 → AI-08 → AI-07. Для AI-06 и AI-02 нужны фото
реальных карток и таблиц из больницы.
